# 攻略・推奨データの更新運用

妻を含むアプリ利用者には更新操作を求めない。アプリは公開攻略サイトを実行時に巡回せず、確認済みの静的データだけを配信する。

## 定期確認

- Codex側の隔週確認で、新キャラ・推奨スキル・オバロ・キューブ・掲載編成の変更有無だけを調べる。
- 変更がない時は通知もコード変更も行わない。
- 1回の確認ではNikkers APIを原則1リクエスト、各攻略ページを各1回まで開く。連続巡回、並列大量取得、回避目的のプロキシは使わない。
- 差分があった場合も自動公開せず、出典URL・確認日・変更候補を報告してから通常の作業ブランチで反映する。

## Nikkers APIの推奨スキル

開発者が次を実行すると、全キャラの推奨スキル値を1リクエストで取得し、同梱ファイルを更新する。

```powershell
pnpm run data:update-growth
pnpm test
pnpm run build
```

生成先は `src/data/growthRecommendations.ts`。アプリ実行中はNikkers APIへ推奨取得の通信を行わない。

## APIのない攻略情報

オバロ・キューブ・編成は公開APIまたは明示的な再利用条件がない限り、一括スクレイピングしない。公開ページを人が低頻度で確認し、要約・出典URL・確認日だけを静的データへ反映する。本文・画像・表の丸ごと複製は行わない。

### 情報源の選定

- 特定サイトを常に正解とはせず、企業攻略サイト、専門攻略サイト、公式情報、更新が確認できるコミュニティ資料・個人ブログを候補にする。
- 個人ブログは、更新日、対象ステージや戦力差、実戦経験、操作方法が具体的であるかを確認する。主観を含む記事は単独の完成編成根拠にせず、他の独立ソースとの一致を補助材料にする。
- 更新日、対象コンテンツとの一致、完成データの明記、理由・運用説明の有無、他ソースとの整合を比較する。
- 複数の独立した情報源で同じ完成編成、または同じ中核メンバーが繰り返し掲載されている場合は、頻出度を裏付けとして扱う。ただし転載・参照関係にある記事は独立した1票として数えない。
- 同じ条件なら、更新が新しく、編集主体と根拠が明確で、実戦条件まで説明された情報を優先する。
- 編成は複数サイトのメンバーを混ぜて独自の5人を作らず、採用元に掲載された完成形をそのまま収録する。
- 評価が割れる場合は断定せず、用途や条件の違いを注記する。更新日だけを理由に、内容の薄い情報へ置き換えない。
- 頻出していても古い編成は最新メタとは扱わず、新キャラ・仕様変更後の記事と照合する。
