# 設計・検証メモ

## 構成

- `src/api/nikkeApi.ts`: API通信、共通形式への変換、BlablaLink ID抽出、非破壊マージ
- `src/storage.ts`: localStorageスキーマv2、初期値、インポート検証
- `src/rules/teamBuilder.ts`: 編成の決定論ルール
- `src/rules/growth.ts`: BlablaLink取込値の参照と育成目標との差分
- `src/pages/`: ホーム、ニケ一覧、編成、設定
- `public/sw.js`: アプリシェルと公開マスターデータのキャッシュ。`/api/user/` は対象外

API一覧は起動時に1回だけ取得し、検索と絞り込みは取得済み配列だけで行います。詳細はカードを開いた時だけ取得し、同じ画面セッション中は再利用します。個人入力だけをlocalStorageへ保存し、画像や全キャラ詳細JSONは保存しません。

## 保存と取り込み

保存データは `nikke-compass:data`、スキーマバージョンは3です。BlablaLink取り込み値は `record.imported` に保存し、現在値の表示はこの取込値を優先します。旧版の手入力値はバックアップ互換のため削除せず保持しますが、現在値として編集するUIは提供しません。共有URLは保存せず、openidはバックアップ対象外の接続専用キーに保存します。ユーザーAPIの内部IDは図鑑IDと異なるためresourceIdで照合します。

## 編成ルールの範囲

所持編成では所持フラグを最優先し、レベル、スキル、装備、オバロ、戦闘力を選出順位に使いません。配置は固定バーストⅠ、固定バーストⅡ、バーストⅢ、次のバーストⅢ、補助の順を基本にします。20秒CTの既知キャラ、40秒の交互使用、正式名称が完全一致する「レッドフード」のⅠ・Ⅱ各1回という再突入を区別します。「ラピ：レッドフード」は別キャラとして扱います。

参考目標編成は所持・未所持に関係なく図鑑全体へ同じルールを適用します。APIは最適編成を返さず、アプリ内で登録した代表役と属性による独自推定です。異常個体は機構上の手動操作を完全再現できないため「手動推奨」です。

オバロ推奨はNikkers公開APIのキャラ別notesを2026-11-03に確認し、resourceIdで静的に対応付けます。ブラウザ実行時にはNikkersへ通信せず、未確認resourceIdへ推測を流用しません。機能改修とは別に、新キャラ追加・既存ビルド変更時をデータ更新タイミングとします。

オバロ目標は取込済み効果名と推奨効果を照合し、現在本数、公開情報に数値がある最低目標、次に狙う効果を端末内で算出します。推奨本数が不明な場合は数値を作らず「未付与」とします。ランク12〜14は青字、ランク15は黒帯として表示し、装備固有名と装備IDは画面に出しません。推奨情報の起動時通信や定期ポーリングは行いません。

## 重点検証

- 390×844と430×932で横方向にはみ出さず、下部ナビがホームインジケーターを避ける
- 文字入力が16px以上でSafariの自動拡大を起こしにくい
- 検索、5種絞り込み、所持・育成切替が即時反映される
- 再読み込みでlocalStorageが復元される
- JSON書き出し→読み込みで復元され、上書き前に確認が出る
- バーストⅠ→Ⅱ→Ⅲと継続CTを区別する
- ID 447001（レッドフード）と201601（ラピ：レッドフード）を別レコードとして扱う
- API失敗時に保存済みレコードと内蔵最小カタログで操作を継続する
